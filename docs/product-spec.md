# CoDrop「一起买」最小 POC 产品与技术规格

版本：POC v0.1  
目标：在 Monad 测试网上跑通 **一个人付款 → 多个地址收到 Pass → 主办方与平台分别提款**。

执行拆解：[开发任务与验收条件](./implementation-tasks.md)。技术选型与 Monad 配置于 2026-09-05 核对；任务未勾选前均为待实现。

本规格替代原 PRD v1.0 的功能范围与验收要求。原有双人签名、多志愿、抽签、退款等功能不进入本次交付。以下均为待实现要求，不表示已经完成。

## 1. 产品定位

CoDrop 是一个支持代买的限量 Pass 发售页面。POC 使用模拟小游戏 **「Monad Relay 链上接力」** 作为演示背景：1–5 名玩家组队夺回能量核心，队长一次付款，为整队领取入场 Pass。

游戏主办方提供固定数量的 Pass。队长填写队员的钱包地址，一次支付全部入场费；库存足够时，所有地址在同一笔交易中收到 Pass，平台按成交额收取 1% 服务费。

小游戏仅提供业务叙事和静态视觉，不实现关卡、积分、对战或 Pass 验权。POC 要验证的是“一人付款、多人同时收到链上凭证”的购买闭环。

对外文案：

> 一次付款，帮朋友一起买好。名额够就全部成功，不够就整单不成交。

这里的“报名成功”就是“购买成功”，没有等待分配或中签的阶段。

## 2. 固定演示范围

| 项目 | 本版约定 |
|---|---|
| 网络 | Monad Testnet |
| 支付资产 | 测试 MON |
| 活动 | Monad Relay 模拟小游戏、一个场次 |
| 当前演示库存 | 1000 张 Pass，方便重复测试 |
| 当前演示单价 | 每人 0.01 测试 MON |
| 单笔购买人数 | 1–5 人 |
| 每个接收地址 | 同一订单内只出现一次，每次收到一枚 Pass |
| 付款人 | 可以包含在接收名单中，也可以完全替别人购买 |
| 平台费 | 成交金额的 1%，从主办方收入中扣除 |
| 配置方式 | 部署时设置，不做活动创建后台 |
| 购买顺序 | 按链上交易实际执行顺序，先买先得 |
| 完成标准 | 真实测试网购买、发证、记账和提款均可核查 |

单笔最多 5 人只用于限制演示规模，不增加多人组队系统。

## 3. 用户与权限

| 角色 | 可以做什么 |
|---|---|
| 购买者 | 查看活动、填写接收地址、支付整单票款、查看交易 |
| Pass 接收者 | 无需签名或付款，接收并查看自己的 Pass |
| 主办方 | 提取已成交金额中的 99% |
| 平台 | 提取已成交金额中的 1% |
| 部署者 | 部署时设置活动参数；部署后没有改价、增发、改收款人或提走全部余额的权限 |

代买只是赠送资格，**不代表接收者已经确认参加**。

不做每地址只能购买一次的限制。同一个地址可以在不同订单中再次收到 Pass；不会因为别人替它买过，就失去购买资格。

## 4. 最小用户流程

1. 打开活动页面，查看单价、剩余库存及测试网提示。
2. 连接钱包。
3. 填写接收地址，每行一个。
4. 页面展示购买人数和总价。
5. 点击购买，付款钱包确认一笔交易。
6. 等待交易成功回执。
7. 显示购买成功、接收地址和交易链接。
8. 主办方与平台连接各自钱包，分别提取收入。

不需要接收者在线，不需要邀请链接，也不需要额外领取 NFT。

## 5. 购买与库存规则

合约必须检查：

- 接收人数为 1–5。
- 接收地址不能为零地址。
- 同一订单内没有重复地址。
- 剩余库存不少于购买人数。
- 实际付款严格等于“人数 × 单价”。

所有检查、库存扣减、NFT 铸造和收入记账在**同一笔交易中完成**。

任意一步失败，整笔交易回滚：

- 不发出部分 Pass。
- 不扣减库存。
- 不形成任何平台或主办方收入。
- 票款不留在合约中；失败交易仍可能消耗网络费。

页面显示的库存只作提交前参考。即使页面刚显示有库存，也可能被其他交易先买走；最终以合约执行结果为准。

## 6. Pass 定义与边界

本版使用 **ERC-721 NFT**，每张 Pass 有独立的 `tokenId`。

| 项目 | 约定 |
|---|---|
| 发放时间 | 购买成功时直接铸造 |
| 接收对象 | 购买者填写的地址 |
| 内容 | 游戏名称、模拟入场说明、统一图片 |
| 唯一标识 | 合约地址 + tokenId |
| 图片与元数据 | 固定静态资源，不做上传后台 |
| 查询依据 | 链上 NFT 所有权 |
| 转让 | 使用标准 ERC-721 行为，允许转让 |
| 核销 | 不做 |
| 实际游戏接入 | 不做；仅使用 mock 业务背景 |

**本版不实现不可转让限制。** 因此，接收地址是最初领取人，之后的持有人可能变化；页面不能把“最初购买名单”当成永久持有人名单。

所有 Pass 可使用同一份静态元数据，不需要逐张生成图片。外部钱包是否自动显示图片不作为验收条件。

演示使用普通钱包地址。若接收地址是不能接收 NFT 的合约地址，安全铸造失败应使整单回滚，不能跳过该地址继续成交。

## 7. 收费与提款

按每笔成功订单计算费用，使用链上整数金额：

```text
订单金额 = 接收人数 × 单价
平台收入 = 订单金额 × 100 ÷ 10,000，向下取整
主办方收入 = 订单金额 − 平台收入
```

例如购买 3 张，每张 0.01 MON：

| 项目 | 金额 |
|---|---:|
| 买家支付票款 | 0.03 MON |
| 主办方待提款增加 | 0.0297 MON |
| 平台待提款增加 | 0.0003 MON |
| 库存减少 | 3 张 |

网络费由发起对应交易的钱包承担，不包含在上述金额中。

采用**先记账、后提款**：

- 购买时只增加双方的待提款余额。
- 主办方和平台分别发起提款。
- 每次提取对应账户的全部待提款金额，不做自定义提款数量。
- 提款收款地址在部署时固定。
- 提款成功后，对应待提款余额归零。
- 转账失败时，整笔提款回滚，待提款权保留。
- 不能重复提取或替另一方取款。
- 购买和提款入口均防止重入。

不提供任意清空合约余额的管理员入口。意外收到的资金不计入成交额，也不增加佣金。

## 8. 技术栈

按全新、独立 POC 选择以下组合：

| 层级 | 技术 | 用途 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 单页应用、表单和交易结果 |
| 样式 | 普通 CSS | 完成基本布局和状态展示 |
| 钱包与链交互 | wagmi + viem 2.x（>= 2.40.0）+ TanStack Query | 使用 injected 浏览器钱包连接、合约读取、交易发送和状态刷新 |
| 智能合约 | Solidity + OpenZeppelin Contracts | ERC-721、购买逻辑、佣金记账、提款保护 |
| 合约测试与部署 | 官方 Foundry >= 1.8.0 | 启用 Monad 执行环境，本地测试、部署脚本和合约验证 |
| 网络 | Monad Testnet | 真实测试交易 |
| 页面托管 | 任意静态托管服务 | 发布构建后的前端及静态图片、元数据 |

wagmi 基于 viem，并使用 TanStack Query 管理相关缓存与响应式状态；OpenZeppelin 提供 ERC-721 等标准实现。[wagmi 官方说明](https://wagmi.sh/)、[OpenZeppelin 文档](https://docs.openzeppelin.com/contracts)

Monad 测试网 Chain ID 为 `10143`，默认 RPC 为 `https://testnet-rpc.monad.xyz`，浏览器使用 `https://testnet.monadvision.com`。部署前再次核对网络及 hardfork，并统一写入前端配置。[Monad 测试网配置](https://docs.monad.xyz/developer-essentials/testnet)

Foundry 配置 `network = "monad"`；本地 hardfork 必须与目标测试网对齐，不能直接依赖工具的最新默认值。[Monad Foundry 指南](https://docs.monad.xyz/tooling-and-infra/toolkits/foundry)
支付页面参考 https://hosted-checkout.demos-crossmint.com/ 

**不需要 Next.js 服务端、数据库、Redis、索引器、API 服务或定时任务。** 如果实际项目已经有能运行的 Next.js 前端，则继续沿用，不为本规格迁移框架。

开工时锁定依赖与编译器版本，交付保留锁文件和 Foundry 配置。

## 9. 最小技术结构

```text
浏览器页面
   │
   ├─ 钱包连接与用户确认
   │
   └─ Monad RPC
          │
          └─ 一个 CoDropPass 合约
                 ├─ ERC-721 Pass
                 ├─ 库存与购买
                 ├─ 主办方待提款余额
                 └─ 平台待提款余额
```

一个业务合约即可，不做工厂、代理升级或多个合约之间的结算。

建议仅提供三个业务写入入口：

| 入口 | 职责 |
|---|---|
| `buy(address[] recipients)` | 收取准确票款，整单发 Pass，扣库存并记账 |
| `withdrawOrganizer()` | 主办方提取收入 |
| `withdrawPlatform()` | 平台提取佣金 |

只读信息包括单价、总库存、已售数量、收款地址、双方待提款余额，以及标准 NFT 所有权查询。

购买事件至少记录付款人、接收地址列表、起始 tokenId、成交金额与平台费；提款事件记录收款人和金额。不要为这些数据再维护一份后端数据库。

## 10. 单页内容与状态

一个页面分为三块：

| 区域 | 必须展示 |
|---|---|
| 活动信息 | 名称、说明、单价、剩余库存、测试网提示 |
| 购买区域 | 钱包连接、接收地址输入、人数、总价、购买按钮和结果 |
| 收入区域 | 两方待提款金额；对应账户连接后显示提款按钮 |

地址表单支持每行一个地址，忽略空行；重复地址明确报错，不静默去重后改变购买人数。

交易状态统一为：

```text
待提交 → 等待钱包确认 → 链上处理中 → 成功 / 失败
```

取得交易哈希只表示已提交，不能提前显示购买成功或提款到账。

本项目选择在成功回执所属区块达到 `finalized` 后显示成功；通过 RPC 查询确认，不用固定延时推算。查询中断时保留交易链接并显示“暂时无法确认”。[Monad 交易时序说明](https://docs.monad.xyz/developer-essentials/summary)

RPC 查询失败时显示“暂时无法确认”，不能把查询失败显示成库存为零、未购买或余额为零。

刷新后重新读取链上库存、当前钱包 Pass 数量与待提款余额。不要求恢复完整历史订单列表；订单明细可以通过交易链接核查。

## 11. 五项验收

| 编号 | 操作 | 通过条件 |
|---|---|---|
| P01 多人购买 | 在当前库存下，付款人替三个不同地址购买 | 只需付款钱包操作；三个地址各收到一枚 Pass；库存减少 3 |
| P02 佣金闭环 | 完成上述 0.03 MON 订单后，双方提款 | 合约向主办方记账 0.0297 MON，向平台记账 0.0003 MON；提款后待提款归零；钱包净增额需扣除各自支付的 Gas |
| P03 整单失败 | 剩余库存 2 时购买 3 张 | 交易失败，无新增 NFT、无库存变化、无新增收入 |
| P04 基础保护 | 检查空名单、零地址、重复地址、超人数、错误金额、越权及重复提款 | 被底层规则拒绝；发证或提款失败不留下部分状态 |
| P05 可验证性 | 刷新页面并核对交易 | 链上库存、NFT 所有权与余额一致；购买和提款有测试网证据 |

P01、P02、P05 必须实际在测试网完成。P03、P04 可以通过本地合约测试验证，不要求在公开网络逐项制造失败。

合约测试集中在一个测试文件，覆盖上述资金、库存与原子性规则；同时检查接收方回调失败、提款失败和重入不会破坏余额。前端完成一轮人工测试网验收即可，本版不强制增加端到端测试框架。

## 12. 明确不做的范围

| 不做 | 本版处理方式 |
|---|---|
| 多活动、多场次、志愿顺序 | 一个活动、一个场次 |
| 抽签和随机服务 | 先买先得 |
| 双方确认、邀请、签名撤销 | 付款人直接填写接收地址 |
| 报名托管、落选退款、超时终止 | 即时成交；失败交易回滚 |
| 购买成功后的退款 | 不支持 |
| 每人限购、白名单、反女巫 | 不限制跨订单重复购买 |
| 单独领取 NFT | 购买时直接发放 |
| 不可转让 Pass | 保留标准转让行为 |
| 真实关卡、积分、检票和游戏验权 | 使用 Monad Relay 静态 mock 背景，仅证明 NFT 已交付 |
| 活动创建与管理后台 | 部署脚本固定配置 |
| 平台数据报表与完整订单中心 | 链上读数和交易链接 |
| 稳定币、AA 分摊、Gas 代付 | 付款人使用测试 MON 全额支付 |
| 合约升级、动态费率 | 部署后固定 |
| 主网上线 | 仅测试网演示 |

购买者填错地址但交易成功时，不提供撤销、强制回收或补发。页面付款前应完整展示接收名单供核对。
